Template versions let you create snapshots of your templates, control which version is active, and schedule version publishing. This enables safe iteration on templates while maintaining a stable production version.

## How Versioning Works

Each template can have multiple versions:

```
Template: "order-confirmation"
├── Version 1 (created Jan 1)
├── Version 2 (created Jan 15)
└── Version 3 (active, created Feb 1)
```

Only one version can be active at a time. When you send emails using this template, the **active version** is used.

## Saving vs. Publishing

This is the most important thing to understand about versions: **saving a template does not change what your application sends.**

| Action | What happens |
|-|-|
| **Save** in the editor | Creates a new version that is **inactive** (a draft). Nothing changes for emails sent through the API. |
| **Publish** a version | Makes that version **active**. From now on, sends by template slug use it. The previously active version becomes inactive. |

So after editing a template there are always two steps: save, then publish. If you add a button, save, and then trigger an email from your application, the email still comes from the previously published version — the new button is missing until you publish the version that contains it.

<Warning>
  A change that shows up in the editor and in the editor's preview but is missing from the email your application sent is almost always an unpublished version. Open the template, click **See versions**, and check which version is marked active.
</Warning>

The template detail page tells you which state you are looking at: the header reads **"This version is currently Active in production"** or **"This version is not active in production"**.

<Note>
  Templates created or updated through the [Template API](/learn/templates/introduction#template-api) behave differently: an API update publishes the new version immediately.
</Note>

## Viewing Versions

On the template detail page:

1. Open a template
2. Click **See versions** to open the **Version History** panel
3. View all versions with their status and creation dates

Each version shows:

| Field | Description |
|-------|-------------|
| Version number | Sequential version identifier |
| Status | Active, Inactive, or Scheduled |
| Created | When this version was created |
| Publish date | When the version will become active (if scheduled) |

## Creating a New Version

You don't create versions by hand — every time you click **Save** in the editor, Lettr snapshots the template as a new version:

- The current template content (HTML and JSON) is copied to the new version
- The version number auto-increments
- The merge tags used in the content are detected and stored with the version
- The new version is **inactive** until you publish it

## Publishing a Version

<Steps>
  <Step title="Open the Template">
    Navigate to the template's detail page.
  </Step>
  <Step title="Open Version History">
    Click **See versions**.
  </Step>
  <Step title="Publish">
    Open the menu (**⋯**) on the version you want to go live and choose **Publish**. In the **Publish Version** dialog, leave the date empty to publish immediately, or pick a date and time to [schedule it](#scheduled-publishing).
  </Step>
</Steps>

The same menu lets you **Compare** a version with another, **Show email** to preview it, and **Delete** inactive versions.

## Active vs Inactive Versions

### Active Version

The active version is used when sending emails:

```javascript
// This uses the active version
await lettr.emails.send({
  from: 'you@example.com',
  to: ['recipient@example.com'],
  subject: 'Your Order',
  template_slug: 'order-confirmation'
});
```

Only one version per template can be active. When you activate a version, the previously active version becomes inactive.

### Using a Specific Version

Override the active version by specifying a version number:

```javascript
// Use version 2 specifically
await lettr.emails.send({
  from: 'you@example.com',
  to: ['recipient@example.com'],
  subject: 'Your Order',
  template_slug: 'order-confirmation',
  template_version: 2
});
```

<Note>
  When no version is specified, Lettr always uses the active version. Use specific versions for testing or when you need to send an older version.
</Note>

## Scheduled Publishing

Schedule a version to become active at a future date:

1. Click **See versions** and choose **Publish** on the version
2. Pick a date and time in the **Publish Version** dialog
3. The version will automatically activate at that time

Use scheduled publishing to:

- Plan template updates ahead of time
- Coordinate template changes with marketing campaigns
- Deploy changes during low-traffic periods

```
Version 3: Active now
Version 4: Scheduled to publish Jan 15 at 9:00 AM
```

When Version 4's publish time arrives, it automatically becomes active and Version 3 becomes inactive.

## Merge Tags (Template Variables)

Each version can define its required merge tags (template variables):

```json
{
  "merge_tags": [
    { "key": "customer_name", "required": true },
    { "key": "order_id", "required": true },
    { "key": "order_total", "required": false }
  ]
}
```

| Field | Description |
|-------|-------------|
| `key` | Variable name as used in the template (e.g., `{{customer_name}}`) |
| `required` | Whether this variable must be provided when sending |

<Warning>
  Include every merge tag the template uses in `substitution_data` when sending. A merge tag with no matching value renders as **empty text** — the email is still sent, with a blank where the value should be (or a link with an empty address). Names are case-sensitive, so `customer_name` does not fill `{{CUSTOMER_NAME}}`.
</Warning>

## Editor Type

Templates can be created with different editor types:

| Editor Type | Description |
|-------------|-------------|
| `topol` | Created with the visual drag-and-drop Topol editor |
| `custom_html` | Created with custom HTML code |

The editor type is stored per version, allowing you to switch between visual and code editing across versions.

## Reverting to a Previous Version

To restore an older version:

1. Open the template and click **See versions**
2. Find the version you want to restore
3. Open its menu and choose **Publish** to make it the active version

This immediately makes the selected version active for all future sends.

<Tip>
  Because every save creates a version and the published one stays active, you can iterate freely: nothing you save reaches recipients until you publish it, and the previous version is always there to roll back to.
</Tip>

## Deleting Versions

You can delete inactive versions to clean up old iterations:

1. Open the template and click **See versions**
2. Find the version to delete
3. Open its menu and choose **Delete**

<Note>
  The delete option is not offered for the active version. Publish a different version first if you need to remove it.
</Note>

## Version Workflow

A typical versioning workflow:

```
1. Edit the template and click Save (creates a new inactive version)
2. Test with the editor preview and test emails
3. Open See versions and Publish the new version (or schedule it)
4. Send through the API — the published version is now used
5. Previous version remains available for rollback
```

To test an unpublished version through the API before it goes live, pass its number as `template_version` — see [Using a Specific Version](#using-a-specific-version).

### Best Practices

1. **Version before major changes**: Create a version before redesigning a template
2. **Use scheduled publishing**: Schedule major changes for optimal timing
3. **Keep a working version active**: Always have a tested, stable version active
4. **Document changes**: Use version numbers to track what changed between versions
5. **Clean up old versions**: Delete versions you no longer need to keep the list manageable

## Version Comparison

Compare versions by:

1. Opening a version's preview
2. Opening another version's preview in a new tab
3. Comparing the rendered output side-by-side

This helps verify changes before activating a new version.

## API Usage

When using templates via API, version behavior follows these rules:

| Scenario | Version Used |
|----------|--------------|
| No version specified | Active version |
| `template_version: 2` | Version 2 (if exists) |
| Version doesn't exist | Error returned |
| All versions inactive | Error returned (generic "template not found") |

```javascript
// Get template details
const response = await fetch(
  'https://app.lettr.com/api/templates/order-confirmation',
  {
    headers: {
      'Authorization': 'Bearer lttr_xxxxxxxxxxxx'
    }
  }
);

const template = await response.json();
console.log(template.data.name); // "Order Confirmation"
console.log(template.data.slug); // "order-confirmation"
```
