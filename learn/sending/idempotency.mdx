A retried send can deliver the same email twice. A network timeout hides whether the first attempt reached Lettr, and queue consumers and serverless platforms invoke the same handler more than once. The `Idempotency-Key` header is the fix: **reusing the same key, payload, and API key within 24 hours returns the original transmission result** without sending another email.

## The contract

Send an optional `Idempotency-Key` header with `POST /api/emails`. Reusing the same key, payload, and API key within 24 hours returns the original transmission result without sending another email. Replayed responses include `Idempotency-Replayed: true` and the same `data.request_id`. Requests without this header are processed independently.

The rules that follow from it:

- **Key format.** Keys are 1 to 255 characters using letters, numbers, `.`, `_`, and `-`.
- **One key per intended email.** A new intended email requires a new key. Reusing a key with a different payload returns `409 idempotency_key_conflict` rather than a second send.
- **Retention is 24 hours.** This is not an unlimited exactly-once guarantee. A retry after the window is a new request and sends a new email.
- **Metadata does not deduplicate.** `metadata.idempotency_key` is stored and echoed in webhooks like any other metadata field. Only the header enables deduplication.

## Choosing a key

Derive the key from the business event the email belongs to, not from the attempt. **Generate or derive one key per intended email, then reuse it across every retry and handler invocation.** Do not generate a new timestamp, random value, or attempt counter for each retry. A UUID generated once and persisted with the business record works as well as a derived key.

```javascript
const idempotencyKey = `order-confirmation-${orderId}`;
```

Include the email's purpose and the entity it relates to, such as `order-confirmation-{order_id}` or `password-reset-{reset_request_id}`. Use a stored identifier rather than a raw token or other user-facing value, which can contain characters outside the allowed key format. A generic key like `email-123` lets two different email types collide on the same value.

## Sending with a key

The header goes on the request alongside the authorization header. A replayed response carries the `Idempotency-Replayed` header and the original `data.request_id`:

```javascript
const response = await fetch('https://app.lettr.com/api/emails', {
  method: 'POST',
  headers: {
    'Authorization': `Bearer ${process.env.LETTR_API_KEY}`,
    'Content-Type': 'application/json',
    'Idempotency-Key': `order-confirmation-${order.id}`,
  },
  body: JSON.stringify({
    from: 'orders@example.com',
    to: [order.customer_email],
    subject: `Order #${order.id} confirmed`,
    template_slug: 'order-confirmation',
    substitution_data: { order_id: order.id, total: order.total },
    metadata: { order_id: order.id },
  }),
});

const data = await response.json();

if (response.headers.get('Idempotency-Replayed') === 'true') {
  console.log('Replayed earlier send', data.data.request_id);
}
```

Store `data.data.request_id` on the order record. The request ID is the handle for delivery status in the API and dashboard, and every webhook event for the message carries it, so a handler can map events back to the order.

## Retrying with the same key

A timeout (`ETIMEDOUT`) or connection reset (`ECONNRESET`) means the client received no response, but Lettr may already have accepted the email. **Retry with the same key and the same payload.** If the first attempt got through, the retry returns the original result as a replay; if it did not, the retry sends the email. There is no need to query for the earlier attempt before retrying.

Keep the payload byte-for-byte identical across retries and across function invocations. For template sends, the resolved content must not change either, which means both `substitution_data` and the template itself stay unchanged between attempts. Pass only the fields the template needs rather than a whole mutable record like the order object, so an unrelated update between attempts cannot alter the payload. A changed payload under the same key is a conflict, not a replay.

```javascript
const sleep = (ms) => new Promise((resolve) => setTimeout(resolve, ms));

async function sendWithRetry(payload, idempotencyKey, maxRetries = 3) {
  const body = JSON.stringify(payload);
  let lastError;

  for (let attempt = 1; attempt <= maxRetries; attempt++) {
    let response;
    try {
      response = await fetch('https://app.lettr.com/api/emails', {
        method: 'POST',
        headers: {
          'Authorization': `Bearer ${process.env.LETTR_API_KEY}`,
          'Content-Type': 'application/json',
          'Idempotency-Key': idempotencyKey,
        },
        body,
        signal: AbortSignal.timeout(30_000),
      });
    } catch (error) {
      // Network failure or timeout. The same key makes the retry safe either way.
      lastError = error;
      await sleep(Math.pow(2, attempt) * 1000);
      continue;
    }

    // Gateway errors can carry a non-JSON body. Decide from the status either way.
    const data = await response.json().catch(() => ({}));
    if (response.ok) {
      return data;
    }

    const retryable =
      response.status >= 500 ||
      response.status === 429 ||
      data.error_code === 'idempotency_in_progress';

    if (!retryable) {
      throw new Error(`${data.error_code}: ${data.message}`);
    }

    lastError = new Error(`${response.status} ${data.error_code}: ${data.message}`);
    const retryAfter = Number(response.headers.get('Retry-After'));
    await sleep(retryAfter ? retryAfter * 1000 : Math.pow(2, attempt) * 1000);
  }

  throw lastError;
}
```

A local sent flag on the business record still saves an API call when the outcome is already known, but it is an optimization. The header is what prevents the duplicate.

## Error responses

Two `409` responses are specific to idempotent requests. The rest of the retry rules are unchanged and covered in [Errors & Retries](/learn/sending/errors-retries).

| Response | Meaning and action |
|-|-|
| `409` `idempotency_in_progress` | The original request is still being processed. Retry the same request after `Retry-After`. |
| `409` `idempotency_key_conflict` | The key was reused with a different payload. Use a new key for a new email, or send the original payload. |
| `422` `validation_error` | Correct the invalid key or payload. |
| `429` | Rate limits and quotas still apply, including to retries. |
