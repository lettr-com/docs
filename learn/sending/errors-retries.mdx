A send request can fail on invalid parameters, an unverified domain, a rate limit, or a transient server problem, and each of those wants a different response from the caller. This page covers the error format, the codes worth handling by name, which responses are safe to retry, and a retry pattern that respects `Retry-After` and the `Idempotency-Key` header.

## Error response format

Every error is a JSON object with the same shape. **`error_code` identifies the category of failure**, `message` is a human-readable description, and `errors` (present on validation failures only) maps each invalid field to its problems:

```json
{
  "error_code": "validation_error",
  "message": "The given data was invalid.",
  "errors": {
    "to": ["The to field is required."],
    "subject": ["The subject must not exceed 998 characters."]
  }
}
```

## Common error codes

| Error code | HTTP status | Description |
|-|-|-|
| `validation_error` | 422 | Invalid request parameters or an invalid `Idempotency-Key` |
| `invalid_domain` | 400 | Sender domain not verified |
| `unconfigured_domain` | 400 | Domain not ready for sending |
| `template_not_found` | 404 | Template slug not found |
| `idempotency_in_progress` | 409 | The original request with this `Idempotency-Key` is still being processed |
| `idempotency_key_conflict` | 409 | The `Idempotency-Key` was reused with a different payload |
| `rate_limit_exceeded` | 429 | Too many requests; wait for `Retry-After` |
| `quota_exceeded` | 429 | Monthly or daily sending quota reached |
| `send_error` | 500 | Email sending error |
| `transmission_failed` | 502 | Email delivery to upstream provider failed |

## Validation errors

A `422` means the request was well-formed but carried invalid data: a missing required field, a malformed recipient address, or a subject over the length limit. The `errors` object names the field, so a handler can report the specific problem:

```javascript
try {
  await lettr.emails.send(emailData);
} catch (error) {
  if (error.status === 422) {
    console.log('Validation errors:', error.errors);

    if (error.errors.to) {
      console.log('Invalid recipients:', error.errors.to);
    }
    if (error.errors.from) {
      console.log('Invalid sender:', error.errors.from);
    }
  }
}
```

<Note>
  An unverified or misconfigured sending domain is **not** a validation error. It returns `400` with
  `invalid_domain` or `unconfigured_domain`, so a handler scoped to `422` misses the most common
  first-send failure. SDKs that map only `422` to a validation exception (`lettr-php` raises a
  generic `ApiException` here) will not route it to a validation `catch` block either. See
  [Domain errors](#domain-errors) below.
</Note>

## Domain errors

The `from` address must use a verified domain with its DNS records in place. **These are the most common errors during initial setup**, and they are not retryable until the domain is fixed:

```javascript
try {
  await lettr.emails.send({
    from: 'you@unverified-domain.com',
    to: ['recipient@example.com'],
    subject: 'Hello',
    html: '<p>Hello!</p>'
  });
} catch (error) {
  if (error.error_code === 'invalid_domain') {
    console.log('Domain not verified. Please verify your domain first.');
  }
  if (error.error_code === 'unconfigured_domain') {
    console.log('Domain DNS records not configured correctly.');
  }
}
```

## Retryable and non-retryable errors

Retrying a validation error or an unauthorized request produces the same result every time, so the retry path should only see server failures, rate limits, and an idempotent request that is still in flight. Two `409` codes exist only for requests that carry an `Idempotency-Key`; the [Idempotency guide](/learn/sending/idempotency) covers the header itself.

| Response | Retryable | Meaning and action |
|-|-|-|
| `429` `rate_limit_exceeded` | Yes | Wait for `Retry-After`, then retry. Rate limits and quotas apply to retries too. |
| `409` `idempotency_in_progress` | Yes | The original request is still processing. Retry the same request after `Retry-After`. |
| `500` Server error | Yes | Retry with backoff |
| `502/503/504` Gateway errors | Yes | Retry with backoff |
| `409` `idempotency_key_conflict` | No | The key was reused with a different payload. Use a new key for a new email. |
| `422` `validation_error` | No | Correct the invalid key or payload |
| `401` Unauthorized | No | Check the API key |
| `403` Forbidden | No | Check the API key's permissions |
| `404` Not found | No | Check that the template or resource exists |

## Retry logic

A retry helper needs three things: **a stable `Idempotency-Key` so a retried send cannot deliver twice**, a check that rejects non-retryable errors before backing off, and a delay that honours `Retry-After` when the response carries one. The pattern below uses exponential backoff as the fallback delay:

```javascript
const sleep = (ms) => new Promise((resolve) => setTimeout(resolve, ms));

async function sendEmailWithRetry(emailData, idempotencyKey, options = {}) {
  const {
    maxRetries = 3,
    baseDelay = 1000,
    maxDelay = 30000
  } = options;

  const body = JSON.stringify(emailData);
  let lastError;

  for (let attempt = 1; attempt <= maxRetries; attempt++) {
    let response;
    try {
      response = await fetch('https://app.lettr.com/api/emails', {
        method: 'POST',
        headers: {
          'Authorization': `Bearer ${process.env.LETTR_API_KEY}`,
          'Content-Type': 'application/json',
          'Idempotency-Key': idempotencyKey,
        },
        body,
        signal: AbortSignal.timeout(30_000),
      });
    } catch (error) {
      // Network failure or timeout. Retrying with the same key is safe either way.
      lastError = error;
      await sleep(Math.min(baseDelay * Math.pow(2, attempt - 1), maxDelay));
      continue;
    }

    // Gateway errors can carry a non-JSON body. Decide from the status either way.
    const data = await response.json().catch(() => ({}));

    if (response.ok) {
      if (data.data?.request_id) {
        return data;
      }
      // A 2xx with a truncated or malformed body. The same key replays the original result.
      lastError = new Error('Success response could not be parsed');
      await sleep(Math.min(baseDelay * Math.pow(2, attempt - 1), maxDelay));
      continue;
    }

    const error = Object.assign(new Error(data.message || response.statusText), {
      status: response.status,
      error_code: data.error_code,
      errors: data.errors,
      retryAfter: Number(response.headers.get('Retry-After')) || null,
    });

    const retryable =
      response.status >= 500 ||
      response.status === 429 ||
      data.error_code === 'idempotency_in_progress';

    if (!retryable) {
      throw error;
    }

    lastError = error;

    const delay = Math.min(baseDelay * Math.pow(2, attempt - 1), maxDelay);
    const wait = error.retryAfter ? error.retryAfter * 1000 : delay;

    console.log(`Attempt ${attempt} failed. Retrying in ${wait}ms...`);
    await sleep(wait);
  }

  throw lastError;
}
```

A network timeout is retryable with the same key and payload. If the first attempt reached Lettr, the retry returns the original result with `Idempotency-Replayed: true`; if it did not, the retry sends the email.

## Handling the result

Wrapping the retry helper gives application code a structured result instead of an exception. Log enough context to debug later, and map the codes the caller can act on:

```javascript
async function sendEmail(emailData, idempotencyKey) {
  try {
    const response = await sendEmailWithRetry(emailData, idempotencyKey);
    return { success: true, data: response.data };
  } catch (error) {
    console.error('Email send failed:', {
      error_code: error.error_code,
      message: error.message,
      to: emailData.to,
      timestamp: new Date().toISOString()
    });

    switch (error.error_code) {
      case 'validation_error':
        return { success: false, error: 'Invalid email data', details: error.errors };

      case 'invalid_domain':
        return { success: false, error: 'Sender domain not verified' };

      case 'idempotency_key_conflict':
        return { success: false, error: 'Idempotency key reused with a different payload' };

      case 'rate_limit_exceeded':
        return { success: false, error: 'Rate limit exceeded', retryAfter: error.retryAfter };

      default:
        return { success: false, error: 'Failed to send email' };
    }
  }
}
```

## Soft bounce retries

Retries on the API side end once Lettr accepts the message. From there, **Lettr retries soft bounces from the receiving mail server itself**, so the integration needs no logic for them. Hard bounces are permanent and are never retried:

| Bounce type | Auto-retry | Max attempts |
|-|-|-|
| Soft bounce (mailbox full) | Yes | 3 |
| Soft bounce (server error) | Yes | 3 |
| Hard bounce (invalid address) | No | - |

## Circuit breaker pattern

In high-volume sending, a run of failures usually means a systemic problem rather than a bad request. A circuit breaker stops sending after a threshold of failures, waits out a cooldown, then lets a single test request through before resuming normal traffic:

```javascript
class EmailCircuitBreaker {
  constructor(threshold = 5, resetTimeout = 60000) {
    this.failures = 0;
    this.threshold = threshold;
    this.resetTimeout = resetTimeout;
    this.state = 'closed';
    this.lastFailure = null;
  }

  async send(emailData) {
    if (this.state === 'open') {
      if (Date.now() - this.lastFailure > this.resetTimeout) {
        this.state = 'half-open';
      } else {
        throw new Error('Circuit breaker is open');
      }
    }

    try {
      const result = await lettr.emails.send(emailData);
      this.onSuccess();
      return result;
    } catch (error) {
      this.onFailure();
      throw error;
    }
  }

  onSuccess() {
    this.failures = 0;
    this.state = 'closed';
  }

  onFailure() {
    this.failures++;
    this.lastFailure = Date.now();
    if (this.failures >= this.threshold) {
      this.state = 'open';
    }
  }
}
```

## Monitoring errors

Failures after the API accepts an email never surface in the send response. A webhook handler for bounce and generation-failure events is the place to catch them:

```javascript
app.post('/webhooks/lettr', (req, res) => {
  const event = req.body;

  if (event.type === 'generation.generation_failure' || event.type === 'message.bounce') {
    alertTeam({
      type: event.type,
      email_id: event.data.email_id,
      recipient: event.data.to,
      error: event.data.error_message
    });
  }

  res.sendStatus(200);
});
```
