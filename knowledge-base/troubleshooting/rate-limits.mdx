The Lettr API returns HTTP `429` when a request exceeds a rate limit or a sending quota. This guide covers how to read the response, back off correctly, and tell the different kinds of `429` apart. For the full list of limits and headers, see the [Rate Limit reference](/api-reference/rate-limit).

---

## Which Limit Did I Hit?

| Limit | Applies to | Details |
|-|-|-|
| 3 requests per second | Each team, shared by all of its live API keys | The usual cause of `rate_limit_exceeded` |
| Sandbox limits | [Sandbox API keys](/learn/api-keys/sandbox#rate-limits) only | Separate from the team limit; sandbox traffic never counts toward it |
| Per-IP limits | Requests from a single IP address | Enforced at the network edge (600 requests per 5 minutes on web routes, 2,000 per 5 minutes on API routes) |

<Note>
  Sandbox keys are exempt from the team limit and have their own per-second, per-minute and per-day limits, so a `429` on a sandbox key means you hit a sandbox limit. A live key hitting `429` while another live key is busy is expected: they share one limit.
</Note>

A per-IP `429` can also hit live-key traffic. It comes from the network edge, so it is not produced by the team limiter and its body differs from the one below. On API routes its JSON body uses `error_code` `api_rate_limited` instead of `rate_limit_exceeded`.

A `429` whose body has `error_code` set to `quota_exceeded` or `daily_quota_exceeded` comes from a sending quota rather than a rate limit, so slowing down won't clear it. See [Email Usage & Quotas](/learn/sending/usage-quotas).

## Reading the Response

Exceeding the team limit returns HTTP `429` with this body:

```json
{
  "message": "Rate limit exceeded. Please slow down your requests.",
  "error_code": "rate_limit_exceeded"
}
```

| Header | Meaning |
|-|-|
| `Retry-After` | Seconds to wait before retrying. Only on `429` responses. |
| `X-RateLimit-Limit` | Requests allowed per second (3 for live keys). |
| `X-RateLimit-Remaining` | Requests left in the current window. `0` on a `429`. |
| `X-RateLimit-Reset` | Unix timestamp (seconds) when the window resets. |

Every API response carries the `X-RateLimit-*` headers, so a client can slow down before it gets a `429`. Sandbox keys also get `X-Sandbox-RateLimit-*` headers, described on the [sandbox page](/learn/api-keys/sandbox#rate-limits).

<Warning>
  Requests sent before the window resets are rejected with another `429`. Always respect the `Retry-After` header before retrying.
</Warning>

## Implementing Backoff

On a `429`, pause and retry with exponential backoff. This example reads `Retry-After` and doubles the wait on each attempt:

```javascript
async function sendWithBackoff(url, payload, maxRetries = 5) {
  for (let attempt = 0; attempt < maxRetries; attempt++) {
    const response = await fetch(url, {
      method: "POST",
      headers: {
        "Content-Type": "application/json",
        "Authorization": "Bearer YOUR_API_KEY",
      },
      body: JSON.stringify(payload),
    });

    if (response.status === 429) {
      const retryAfter = Number(response.headers.get("Retry-After")) || 1;
      const backoff = retryAfter * 1000 * Math.pow(2, attempt);

      console.log(`Rate limited. Retrying in ${backoff / 1000}s (attempt ${attempt + 1})`);
      await new Promise((resolve) => setTimeout(resolve, backoff));
      continue;
    }

    return await response.json();
  }

  throw new Error("Max retries exceeded");
}
```

## Sending Fewer Requests

Each request supports up to 50 recipients across `to`, `cc` and `bcc` combined, so fill each request before sending the next. Sending one recipient per request uses up the 3 requests per second for no benefit.

```javascript
function chunkRecipients(recipients, size = 50) {
  const chunks = [];
  for (let i = 0; i < recipients.length; i += size) {
    chunks.push(recipients.slice(i, i + size));
  }
  return chunks;
}

async function sendToAll(recipients, emailPayload) {
  const chunks = chunkRecipients(recipients);

  for (const chunk of chunks) {
    await sendWithBackoff("https://app.lettr.com/api/emails", {
      ...emailPayload,
      to: chunk,
    });

    // Pause between requests to avoid hitting rate limits
    await new Promise((resolve) => setTimeout(resolve, 1000));
  }
}
```

<Tip>
  Sending to 10,000 recipients at 50 per request takes 200 API calls. With a 1-second pause between each, that finishes in under 4 minutes, well within the limit.
</Tip>

Rather than polling the API for email status, use [webhooks](/learn/webhooks/introduction) to receive delivery events. For large sends, see [Batch Sending](/learn/sending/batch-sending).

## Still Getting Unexpected 429s?

For `429` errors well below the limits above, contact [support@lettr.com](mailto:support@lettr.com) with your API key prefix and the timestamps of the affected requests. For higher limits, contact [sales@lettr.com](mailto:sales@lettr.com).
