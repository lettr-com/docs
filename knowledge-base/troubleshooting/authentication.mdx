## Common Errors

### 401 Unauthorized

This error means the API could not authenticate your request. You will receive an HTTP 401 response.

**Error:**
```json
{
  "message": "Invalid API key."
}
```

If the `Authorization` header is missing entirely, the message is `API key is required.` instead.

**Causes & Solutions:**

<AccordionGroup>
  <Accordion title="Missing API Key">
    Every request must include the `Authorization` header with a valid Bearer token:
    ```bash
    curl https://app.lettr.com/api/domains \
      -H "Authorization: Bearer lttr_xxxxxxxxxxxx"
    ```
    If the header is missing entirely, the API will reject the request with a 401 status.
  </Accordion>
  <Accordion title="Invalid Key Format">
    All Lettr API keys start with the `lttr_` prefix. Double-check for:
    - Typos or extra whitespace in the key
    - A missing or incorrect `Bearer ` prefix in the header value
    - Quotes or escape characters accidentally included in the key string
  </Accordion>
  <Accordion title="Revoked or Deleted Key">
    If an API key has been deleted from the dashboard, it immediately stops working. Go to **API Keys** in the Lettr dashboard sidebar to confirm your key still exists and create a new one if needed.
  </Accordion>
</AccordionGroup>

### 403 Forbidden

A 403 response means your key was recognized but is not allowed to perform the requested action. There are two main causes.

#### Insufficient Permissions

**Error:**
```json
{
  "message": "Your API key does not have the required permissions for this action.",
  "error_code": "insufficient_scope"
}
```

Your API key has the **Sending Only** permission level but you are trying to access an endpoint that requires **Full Access** (for example, managing domains or reading analytics).

**Solution:** Create a new API key with **Full Access** permissions under **API Keys** in the dashboard, or use an existing key that already has the required permission level.

#### IP Address Restriction

**Error:**
```json
{
  "message": "Access denied. Your IP address is not allowed."
}
```

The API key has IP restrictions configured and your request is coming from an IP address that is not on the allow list.

**Solution:**

1. Go to **API Keys** in the dashboard sidebar
2. Find the key and check its IP restriction settings
3. Add your server's IP address to the allow list, or remove the restriction if it is no longer needed

<Tip>
If you are unsure which IP your server uses, you can run `curl ifconfig.me` on the machine making the API requests.
</Tip>

## Verifying Your API Key

Run a simple test request to confirm your key is valid and working:

```bash
curl -i https://app.lettr.com/api/auth/check \
  -H "Authorization: Bearer lttr_xxxxxxxxxxxx"
```

**If the key is valid**, you will receive an HTTP 200 response with the message `API key is valid.` and your team ID. This endpoint works with both Full Access and Sending Only keys.

**If the key is invalid**, you will receive an HTTP 401 response:

```json
{
  "message": "Invalid API key."
}
```

<Note>
The `-i` flag includes response headers in the output, which is helpful for debugging.
</Note>

## Correct Authentication Usage

All requests to the Lettr API must include the `Authorization` header with a Bearer token.

**GET request:**
```bash
curl https://app.lettr.com/api/domains \
  -H "Authorization: Bearer lttr_xxxxxxxxxxxx"
```

**POST request:**
```bash
curl -X POST https://app.lettr.com/api/emails \
  -H "Authorization: Bearer lttr_xxxxxxxxxxxx" \
  -H "Content-Type: application/json" \
  -d '{
    "from": "you@yourdomain.com",
    "to": ["recipient@example.com"],
    "subject": "Hello from Lettr",
    "html": "<p>This is a test email.</p>"
  }'
```

<Warning>
Do not pass your API key as a query parameter or in the request body. Always use the `Authorization: Bearer` header.
</Warning>

## Environment Variables

Never hard-code API keys in your source code. Store them in environment variables instead.

**Using a `.env` file:**
```bash
# .env
LETTR_API_KEY=lttr_xxxxxxxxxxxx
```

**Exporting in your shell:**
```bash
export LETTR_API_KEY=lttr_xxxxxxxxxxxx
```

**Using the variable in a curl request:**
```bash
curl https://app.lettr.com/api/domains \
  -H "Authorization: Bearer $LETTR_API_KEY"
```

## Webhook Authentication Issues

Lettr doesn't sign webhook payloads, so there is no signature header to verify. Instead, each webhook is configured with an authentication type — **None**, **Basic**, or **OAuth 2.0** — and Lettr sends the matching credentials with every delivery. Below are common issues and how to solve them.

### Check the Basic Auth Credentials

With Basic authentication, Lettr sends an `Authorization: Basic ...` header built from the username and password you entered when creating the webhook. Your endpoint should decode it and compare both values.

**Express.js -- correct setup:**
```javascript
const express = require("express");
const app = express();

app.post("/webhooks/lettr", express.json(), (req, res) => {
  const authHeader = req.headers.authorization || "";

  if (!authHeader.startsWith("Basic ")) {
    return res.status(401).send("Missing credentials");
  }

  const [username, password] = Buffer.from(authHeader.slice(6), "base64")
    .toString()
    .split(":");

  if (
    username !== process.env.LETTR_WEBHOOK_USERNAME ||
    password !== process.env.LETTR_WEBHOOK_PASSWORD
  ) {
    console.error("Webhook authentication failed");
    return res.status(401).send("Invalid credentials");
  }

  console.log("Verified webhook events:", req.body);

  res.status(200).send("OK");
});
```

### Common Pitfalls

<AccordionGroup>
  <Accordion title="Looking for a signature header">
    Lettr doesn't send a signature header such as `lettr-signature` or `x-signature`. Authenticate requests with the `Authorization` header instead, using the Basic or OAuth 2.0 credentials configured on the webhook.
  </Accordion>
  <Accordion title="Proxy strips the Authorization header">
    Some load balancers, CDNs, and API gateways drop or overwrite the `Authorization` header before it reaches your application. If your credentials look correct but the header arrives empty, check your proxy configuration.
  </Accordion>
  <Accordion title="Wrong webhook credentials">
    Each webhook in the dashboard has its own authentication settings. Make sure the credentials your endpoint checks match the ones configured for that specific webhook. For OAuth 2.0, confirm that the token URL, client ID, and client secret are correct, because Lettr fetches a token from your OAuth server before each delivery.
  </Accordion>
</AccordionGroup>

## Key Security Best Practices

<AccordionGroup>
  <Accordion title="Never commit keys to git">
    Add `.env` to your `.gitignore` file. If a key is accidentally committed, revoke it immediately in the dashboard and create a new one.
  </Accordion>
  <Accordion title="Use environment-specific keys">
    Create separate API keys for development, staging, and production environments. This limits the impact if any single key is compromised.
  </Accordion>
  <Accordion title="Rotate keys regularly">
    Create a new key, update your environment to use it, then delete the old key. Aim to rotate keys at least every 90 days.
  </Accordion>
  <Accordion title="Use minimum permissions">
    If your application only sends emails, use a key with **Sending Only** permissions. Only use **Full Access** keys when you need to manage domains, templates, or other account resources.
  </Accordion>
</AccordionGroup>
